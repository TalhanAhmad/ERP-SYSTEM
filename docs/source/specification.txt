Encova Workspace Build Specification
Prepared for Talha Ahmad Awan and Codex • 7 November 2026 • Version 1.0
1 Purpose and implementation contract
Build a complete internal platform for Encova Solutions with working frontend, backend, and PostgreSQL persistence. Super admins manage people, work, attendance, and settings. Staff receive a personal dashboard with assignments, feedback, attendance, and reports. This is a proposed specification, not evidence of implemented features or passing tests.
The first release must support an end-to-end company day: an invited person logs in, checks in, receives an assignment, reports progress, submits work, receives a review, and checks out. Authorized managers see exceptions and approve requests. Every interactive control must either work against the backend or be explicitly excluded; do not deliver decorative dashboards backed only by mock data.

Scope and exclusions
Included: invitations, profiles, departments and teams, roles, projects, task assignment by username, submissions and review, daily reports, attendance, corrections, leave approval, internship plans, dashboards, notifications, structured tables, audit records, automated checks, deployment instructions, and restore practice.

Link to work artifacts such as PRs and Drive files; binary file uploads are deferred.

2 Architecture and technical choices
Use a modular monolith: one Next.js application, one PostgreSQL database, and a small scheduled job runner using the same services. Separate modules by business responsibility. Do not introduce microservices, a second backend framework, or Redis without a measured need.

Request boundaries
Server Components call authorized query services directly. Client interactions call Route Handlers under /api/v1. Both paths resolve the same verified user context and call shared services. Next.js recommends server-side reads directly from their data source rather than through the app's own HTTP handlers [1].
Route Handlers parse input, enforce session and mutation-origin requirements, call a service, and map errors. Services own permissions, transitions, and transactions. Query modules own database access and safe field selection. Database and service files are server-only; never expose credentials or raw auth records to browser components.

The worker is a separate process, not a separate business backend. Durable jobs and email retries must not depend on a web request staying alive. In-app notifications are stored in PostgreSQL and refreshed on focus and modest polling; real-time sockets are not required for release one.

SUPER_ADMIN and TEAM_LEAD can create projects. The creator becomes project manager. Project managers manage membership and assignments within their projects. Project ownership does not grant access to private employee records. HR admins participate in project work only when explicitly added as members. MEMBER access is scoped by membership, ownership, and assignment, not just the role name.
Enforcement rules
All query paths, count endpoints, exports, autocomplete results, and mutations enforce the same scopes. Generic resource lookups return 404 when the user cannot see the record. Visible but forbidden actions return 403. Never depend on hidden buttons or layouts to enforce access.
Only super admins grant or change privileged roles. HR may invite MEMBER accounts and change ordinary employment details. No one approves their own leave, attendance correction, task submission, or internship review; route such requests to another authorized person. If no independent approver exists, leave the item pending and show the configuration issue. A single-super-admin setup cannot self-approve personal requests.
Keep at least one active super admin using a transaction and a singleton security-settings lock. Deactivation immediately denies new application access; revoke auth sessions as well. Disable cached role claims as the authoritative source. Read current active status and permissions server-side.
Audit policy
Record successful role changes, invitations, deactivation, assignments, reviews, attendance corrections, leave decisions, settings changes, imports, and exports. Include actor, action, object ID, time, request ID, and safe before/after values. Do not record secrets, full private report bodies, or reset tokens. Application audit records are append-only but are not claimed to be tamper-proof against database administrators.

4 People onboarding and company configuration
Account lifecycle
A super admin creates an invitation with email, unique username, employment type, department, team, and intended role. HR can do this only for MEMBER roles. Normalize email and username before checking uniqueness. Usernames use lowercase letters, numbers, dots, underscores, or hyphens, 3–30 characters. They are labels; all relationships use permanent UUID user IDs.
Generate a cryptographically random single-use invitation token, store only its hash, and expire it after 72 hours. Resending revokes the previous token. On acceptance, verify the token and normalized email, create the auth identity using the library's supported server API, and activate the linked profile. Make this retry-safe. If auth provisioning and domain writes cannot share a transaction, retain a pending state and reconcile; do not grant access until both succeed.
Public self-registration is disabled. The invitation acceptance path is the only user-facing account creation path. Use library-managed hashing, verification, reset, and session APIs. Better Auth provides email/password and session-management facilities; configure and test them for the pinned version [2,3]. Do not implement password hashing or homemade cookies.
Bootstrap the first super admin with an explicit local administration command, never the first visitor. Production passwords are never hardcoded or printed. Password reset returns a generic response to prevent email enumeration. Verify email ownership before activation. Invitation and reset emails use the outbox; development routes them to a mail catcher.
Profiles and organization
A profile contains display name, username, work email, employment type, department, primary team, manager, joining date, optional internship end date, work mode, and active status. Private contact details are optional and accessible only to self, HR, and super admins. Exclude national identity numbers, bank details, and salaries from this release.
Departments contain teams. A team has one lead and multiple members; each person has one primary team initially. Team membership and lead changes require audit records. Avoid cycles in manager relationships. Account deactivation preserves all historical records, cancels future reminders, and displays remaining assigned work for reassignment; it must not delete submissions or attendance.
Settings
Store company display name, timezone, workweek, holidays, daily report cutoff, and notification preferences. Schedule policies are effective-dated and snapshotted into attendance days. Suggested demo values only: Monday–Friday, 09:00–17:00, 15-minute grace, 17:00 report cutoff. The admin must confirm actual values before pilot launch. Changing a policy never silently recalculates historical approved records.

5 Projects assignments reviews and daily reports
Assignment workflow
A project manager searches a scoped directory by @username. Show name, username, team, and active state to avoid selecting the wrong person. Save assignee_id rather than the text username. Each task has one accountable assignee, one reviewer, title, instructions, priority, deadline, and project. The assignee and reviewer must be active project members; super admins may review with an explicit audited override. Reviewer and assignee cannot be the same person.
Task states: ASSIGNED, IN_PROGRESS, BLOCKED, IN_REVIEW, CHANGES_REQUESTED, APPROVED, CANCELED. Only the assignee moves between IN_PROGRESS and BLOCKED, starts an assigned task, or submits work. Submission creates an immutable numbered submission record with a summary and validated HTTPS artifact links. Submission moves the task to IN_REVIEW atomically.
The designated reviewer or super admin may APPROVE or REQUEST_CHANGES with feedback; no self-review. Requesting changes moves the task to CHANGES_REQUESTED. A new submission increments the revision number and preserves prior feedback. Approved tasks are read-only until a manager explicitly reopens them with a reason. Managers can cancel unfinished tasks with a reason. Reassigning an in-review task is blocked until its review is resolved or explicitly returned for changes.
Mermaid diagram source
stateDiagram-v2  ASSIGNED --> IN_PROGRESS: Assignee starts  IN_PROGRESS --> BLOCKED: Assignee reports blocker  BLOCKED --> IN_PROGRESS: Blocker resolved  IN_PROGRESS --> IN_REVIEW: Submit revision  CHANGES_REQUESTED --> IN_REVIEW: Resubmit revision  IN_REVIEW --> CHANGES_REQUESTED: Reviewer returns  IN_REVIEW --> APPROVED: Reviewer approves  APPROVED --> IN_PROGRESS: Manager reopens
Cancellation and manager actions are additional guarded transitions documented above. A task is completed for dashboard metrics only in APPROVED, not merely submitted.
Project boundaries
Projects have a manager, status, member list, and archive timestamp. Archive requires no open tasks, or an explicit action canceling them with a reason. Archived projects are readable but immutable. Block removing a member while they own an open task or pending review. Historic access is based on current project membership unless an admin grants access. Remove membership to revoke project visibility.
Daily reports
One report per active person and company work date. Fields: completed work, remaining work, blockers, and optional task links. Reports start DRAFT, become SUBMITTED, and can become ACKNOWLEDGED by the current team lead or super admin. Submitted content is immutable; a lead can return it for revision, retaining an audit snapshot. Leads cannot acknowledge their own report. Team changes affect current access; do not retain former-manager access by default.
Missing reports are calculated only after the configured cutoff for scheduled workdays, excluding approved full-day leave and holidays. HR sees whether a report was submitted, not its private work narrative. Late submissions remain allowed and are marked late. Attendance does not determine work quality.

6 Attendance leave and corrections
Attendance data flow
Keep immutable check events separate from editable attendance summaries. The server timestamps check-in/out; do not trust the browser clock. A person can check in once and check out once for a scheduled date in release one. A unique request key prevents duplicate clicks from duplicating events. One daily summary per person and work date references its schedule assignment and policy snapshot.
Statuses: NOT_DUE, IN_PROGRESS, PRESENT, ABSENT, ON_LEAVE, HOLIDAY, OFF_DAY, NEEDS_REVIEW. Late and early departure are separate flags. The summary records first_in, last_out, gross_minutes, approved adjustment, and final status. Gross time is not payroll time: breaks are not tracked and no paid-hours claim is made.
Before the shift begins, show NOT_DUE. Check-in produces IN_PROGRESS. Valid check-out produces PRESENT with gross elapsed minutes. After shift end plus a configurable closing buffer, a scheduled day with no events becomes ABSENT unless on approved leave; an unclosed check-in becomes NEEDS_REVIEW, never a fabricated check-out. Off-day or holiday check-ins are rejected in release one with an explanation. Overnight shifts are rejected at schedule setup rather than miscalculated.
Correction workflow
The employee submits proposed in/out times, work date, and reason. HR or another super admin approves or rejects. Check-out must follow check-in and both must fit the applicable day-shift policy. Approval changes the effective summary, preserves raw events, and records old/new values plus reviewer. It can convert an absence or missing check-out to PRESENT. The summary version prevents a stale request from overwriting newer facts. Recalculation respects approved corrections.
Leave workflow
Support full-day leave requests initially: type PERSONAL, SICK, or OTHER; inclusive start/end dates; optional private note. Do not calculate entitlement, pay deductions, or legal allowances. Requests transition PENDING to APPROVED, REJECTED, or CANCELED. Staff can cancel pending requests. Canceling approved leave requires an authorized independent approver and an audit entry.
Expand the range into scheduled dates using the effective work calendar; reject requests with no working dates. Prevent overlapping pending or approved requests for the same person/date. Approval is blocked if there are existing check events for affected dates; HR must resolve the conflict explicitly. Check-in is blocked on approved leave. Approval and check-in acquire the same per-person/date lock so they cannot both win concurrently.
Scheduling and dates
Store instants in UTC timestamptz; store work dates as DATE and calculate them in Asia/Karachi. Assign policies by effective date range, with no overlaps per person. Each generated day stores scheduled start/end instants and grace values. For multi-date transactions, acquire locks in ascending user/date order. Exceptions, job retries, and late corrections must produce the same final summary without duplicate records.

7 Internships notifications and spreadsheet views
Internship management
An internship has intern_id, mentor_id, department, start/end dates, status, and learning objective. Mentor must be an active lead or super admin and cannot be the intern. Allow one active internship per intern. HR and super admins manage enrollment and mentor assignment; assigned mentors manage learning plans and feedback.
Learning milestones have title, description, due date, linked work tasks, and status PLANNED, ACTIVE, SUBMITTED, COMPLETED. Interns submit evidence through linked task submissions. A mentor completes a milestone only after its required tasks are approved. Weekly feedback uses strengths, improvements, next actions, and an optional explained rating. Feedback is visible to the intern, assigned mentor, HR, and super admin. Do not generate automated employee rankings or use attendance as a proxy for skill.
Notifications
Persist in-app notifications for task assignment/reassignment, submission, review outcome, leave and correction decisions, mentorship assignment, and report reminders. Notifications contain a safe title and authorized route, not sensitive HR content. Mark read only for the recipient. Revalidate permission when opening the target; a stale notification must not grant access.
Mandatory account emails: invitation, verification, and password reset. Other email notifications are optional preferences. Write domain changes, audit events, notifications, and outbox rows atomically where they share the database. Store a unique event/recipient key to suppress duplicate notifications. Email delivery is at-least-once; document the possibility of a duplicate after an ambiguous provider timeout.
Spreadsheet-style views
Provide People, Tasks, Attendance, and Report Status tables backed by the same business records and services used by detail pages. Include sortable headers, typed filters, column visibility, pagination, saved personal views, keyboard navigation, and clear unsaved/pending states. Persist only allowed columns and validated filters in saved views.
People edits are limited to authorized profile fields. Task cells expose only actions the current user can perform. Attendance values cannot be overwritten directly: the cell opens the correction workflow. No raw spreadsheet route may bypass approval or validation rules.
Bulk task changes: maximum 100 records per request, preview first, validate each item and expected version, apply all-or-nothing in one transaction. For mixed authorization or conflicts, reject the batch with item-level errors. CSV import initially supports new tasks within one managed project only. No attendance or user-account imports in release one. Cap imports at 500 rows, validate headers and usernames, preview errors, then commit atomically with an idempotency key.
CSV exports obey current row and field permissions, omit private fields by default, and neutralize spreadsheet formula prefixes such as =, +, -, and @ in text cells. Exporting does not grant edit access. Actual Google Sheets synchronization remains a separate future integration.

Dashboard contracts
Super admin: active people, present/absent/needs-review counts, overdue open tasks, pending reviews, pending HR requests, missing reports, and operational failures. HR: attendance, leave, corrections, onboarding, internship administration. Leads: their teams' reports, managed project work, review queue, and mentee progress. Members: own assignments, blockers, today's attendance, pending requests, and report status.
Overdue work means a non-canceled, non-approved task past due_at. Review queue counts only current submissions requiring the viewer's review. Attendance statistics cover scheduled eligible people for the selected date; do not count off-days as absent. Every summary count must use the same scope as its drill-down list.
Component and state requirements
Create reusable AppShell, Sidebar, PageHeader, DataTable, FilterBar, Pagination, StatusBadge, UserPicker, DateField, ConfirmDialog, EmptyState, ErrorState, and FormField components. Feature-specific components include CheckInCard, TaskDrawer, SubmissionForm, ReviewPanel, DailyReportForm, CorrectionDialog, and InternshipTimeline.
Every screen needs loading, empty, error, success, and permission-denied behavior. Keep form input on validation failure. Disable duplicate submissions while pending. A 409 conflict preserves local input and offers reload; never silently overwrite. Destructive or consequential actions show the exact affected object and ask for a reason where specified. Use server-confirmed updates for attendance and approvals; do not present them as successful before commit.

The auth identity is not the application authorization record. All application access requires a linked ACTIVE domain user. Keep account provisioning status separate from profile edits. Usernames may change through an audited admin action, but links remain stable because they use UUIDs.
Company settings use a versioned update and security lock. Schedule policy content becomes immutable after use; create a new policy version for changed rules. Assignments apply prospectively. Do not hard-delete referenced users, departments, policies, or teams. Use archive/inactive flags and preserve historical foreign keys.
Suggested database constraints
Use unique normalized identifiers, foreign keys, CHECK constraints for valid date order and nonnegative durations, and database enum or validated text constraints for state values. Cross-record permission rules belong in services. PostgreSQL CHECK constraints are not a general mechanism for checking other rows; use transactions, locks, and suitable uniqueness/exclusion constraints [4].
Reject manager cycles at write time. The last-super-admin invariant is checked under a lock on company_settings. Protect schedule overlaps with an exclusion constraint where supported, or serialize writes under a locked user row and test concurrent insertion. Never implement overlap protection as an unlocked read-then-insert.

Attendance events permit at most one IN and one OUT per attendance day for release one. User ID must match the parent day, using a composite FK or an equivalent enforced write path plus integrity tests. Corrections do not append fictitious raw events. Leave reservations remain active for PENDING and APPROVED requests and are released on rejection/cancellation in the same transaction.
Tasks must belong to their project; active assignees and reviewers must be eligible members. Lock the project when assignments or membership change. A submission's author must be the task's current assignee. A review's actor must match current reviewer authority and differ from the submitter. Reports may link only tasks visible to their author at submission. Render links through permission checks when read later; a retained link is not an access grant. Preserve edited report versions through safe audit snapshots accessible only to the same report scope.

Atomic writes
Task submission: lock task, check expectedVersion and allowed transition, create immutable submission, move task state, add audit and notification/outbox entries, commit. Review: lock task and current submission, ensure it is still the latest unreviewed revision, write one review, transition task, and notify atomically. Duplicate reviews cannot create contradictory decisions.
Attendance: create the day's unique record if absent, lock it, check effective schedule and approved leave, validate event order, append raw event, update summary, and commit. Leave approval locks all relevant attendance-day rows in ascending date order, creating them if necessary, then checks events and updates leave plus summaries. Correction decisions use the same day lock and expected version.
Bulk writes lock affected resources in deterministic ID order. Never make SMTP or HTTP calls inside database transactions. On serialization failures or deadlocks, retry a small bounded number of times; if exhausted, return a retryable conflict without partial success.
Versions and duplicate requests
PATCH and decision endpoints accept expectedVersion. A conditional update that changes zero rows returns 409 STALE_VERSION. Creation, attendance, submissions, imports, and decisions require an Idempotency-Key. Reuse with the same actor/operation/body returns the original result; reuse with different input returns 409. Reserve the key and execute the domain operation atomically so concurrent duplicates cannot both commit. Retain keys for at least 24 hours in the first release and document cleanup.
Indexes and data retention
Start with indexes for task assignee/status/due_at, task project/status, report user/date, attendance user/date, notification recipient/read_at/created_at, audit entity/time, and outbox status/next_attempt_at. The unique constraints already create indexes; avoid duplicating them. Measure with representative seed data and query plans.
Do not automatically purge attendance, feedback, audit, or reports until Encova approves a retention policy. Delete expired invitation/reset artifacts through library-supported cleanup. Exports are streamed rather than retained indefinitely. Use backups and a controlled data-removal process for real data; archival flags are not a substitute for an approved retention policy.

13 API payload examples and validation
Creating an assignment
POST /api/v1/tasks with Idempotency-Key and a verified session. Example values below describe the shape; replace illustrative identifiers with actual UUIDs in executable fixtures.
{  "projectId": "<project UUID>",  "assigneeId": "<person UUID>",  "reviewerId": "<different person UUID>",  "title": "Build the client list API",  "description": "Return paginated clients with validation tests.",  "priority": "HIGH",  "dueAt": "2026-11-12T12:00:00Z"}
Server checks role, project membership, active assignee/reviewer, distinct reviewer, unarchived project, valid deadline, and unknown fields. It creates the task, audit event, and assignment notification in a transaction. Client receives only task DTO fields. The browser resolves @username through GET /users with q and projectId filters; it never sends a username as a foreign key.
Submitting work and recording review
{  "expectedVersion": 3,  "summary": "Implemented pagination and invalid-input handling.",  "artifactLinks": ["https://example.com/review/123"]}
POST /tasks/:id/submissions accepts the above. POST /submissions/:id/review accepts expectedVersion of the task, decision APPROVE or REQUEST_CHANGES, and feedback. Require nonempty feedback for requested changes; preserve every submission and decision.
Attendance and leave
POST /attendance/check-in and check-out take an empty JSON object plus Idempotency-Key. Identity, work date, and timestamps come from the server. Reject client-supplied userId or occurredAt. POST /leave takes startDate, endDate, type, and optional privateNote. POST /corrections takes attendanceDayId, expectedDayVersion, proposedIn, proposedOut, and reason. Approve/reject actions require the request's expectedVersion; approval checks the day version as well.
Validation defaults
Names 1–120 trimmed characters; task title 1–200; descriptions and report sections at most 5000; comments 1–2000; review/correction reasons 1–2000; HTTPS artifact URLs at most 2048 characters each and at most 10 per submission. Treat links as user content; do not fetch arbitrary URLs server-side. Reject unknown mutation fields, invalid dates, invalid enums, and arbitrary sort expressions. Handle empty optional fields consistently as null or omission, documented per endpoint.
Limit JSON bodies to 256 KB and CSV uploads to 2 MB as initial application limits. Return understandable errors rather than truncating silently. Use parameterized SQL for all raw operations. Log diagnostic details privately with requestId; never return stack traces or connection strings.

16 Security background jobs and deployment
Security baseline
Require server-side authorization on every entry path and explicit response field selection. Use library-managed secure HttpOnly sessions and documented CSRF defenses. Custom cookie-authenticated mutation endpoints enforce same-origin requests and CSRF protection. Do not use GET for writes. Disable public registration and test invitation bypass attempts.
Use rate limits for login/reset/invitation endpoints and sensible per-user mutation limits. Limits must work across deployed instances; use platform-supported shared limits or a database-backed implementation, not an unbounded in-process Map. Protect privileged accounts with supported MFA before real-data rollout. No impersonation feature is included.
Keep secrets out of browser bundles, repository files, logs, and documentation. Validate server environment at startup. Use least-privilege application DB credentials and controlled migration credentials. Test row-level access through direct API calls, not just page navigation. Session revocation plus ACTIVE checks protect deactivated accounts.
Worker requirements
Jobs: process email outbox, finalize eligible attendance days, remind missing reports, and clean expired idempotency/invitation artifacts. Jobs are retryable with unique run keys and leases; competing workers must not process the same lease simultaneously. A crashed worker's lease expires. Do not mark an email delivered before the provider accepts it. Expose exhausted retries to super admins without exposing secret payloads.
Attendance reconciliation recomputes from schedule snapshots, raw events, approved leave, and approved corrections; it must preserve approved overrides. Run periodic reconciliation and allow an audited admin retry. No scheduler running means missing automation, not a false healthy status.
Local and production environments
Use separate development, test, and pilot databases. compose.yaml provides local PostgreSQL and a development mail catcher. .env.example lists placeholders for DATABASE_URL, auth secret and base URL, SMTP host/port/user/password/from address, and worker configuration. Exact variable names are finalized for the chosen adapters on Day 1.
Expected scripts: dev, build, start, lint, typecheck, test:unit, test:integration, test:e2e, db:migrate:dev, db:migrate:deploy, db:seed, worker, and bootstrap:admin. Implement these commands using the installed tool versions, not invented CLI syntax. Protect seed/reset commands from production targets.
Release: CI checks, reviewed migration, backup, compatible migration application, application and worker deployment, then smoke tests. Deploy only to an approved host with Node support and persistent PostgreSQL; static export cannot provide this backend. Document rollback compatibility. Test backup restore into a separate DB; a successful backup command alone does not prove recovery. Retain a release checklist and incident runbook before pilot use.

Pilot acceptance journey
Invite a developer and intern; accept both; assign team and schedule. Create a project, add both people, and assign separate tasks with an independent reviewer. Each sees only permitted work.
