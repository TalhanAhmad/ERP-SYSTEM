# Private financial evidence (F19)

A financial file belongs to one real invoice, bill, customer document, supplier document or journal draft through a restricted foreign key. Ordinary ERP attachment/task permissions do not grant financial access. The app requires current ACTIVE selected Super Admin access on every metadata read, upload authorization, completion, scan and download.

The finance bucket encova-finance-evidence is private, with10MiB and PDF/PNG/JPEG restrictions. A restrictive Storage policy denies direct ordinary authenticated/anonymous access even if another permissive policy exists. The server keeps its service key private. Object keys are randomized UUIDs, immutable and independent of display names. Ten active files per source is enforced under a database lock. Removed metadata remains auditable and does not consume quota.

Fresh password/hosted TOTP and a permanent request key authorize a reservation. Bytes go directly to its upload-only signed capability; no financial bytes are posted through a Vercel request body. Completion uses a five-minute actor/file/current-issuer-session intent, validates actual size, SHA256 and type signature, then enters QUARANTINED. Same-key replay retains one file and rotates only its short intent. Selected administrators can resume with new fresh authentication without changing the original uploader.

The approved scanner receives verified bytes, file UUID and purpose challenge. Its response contains status CLEAN/INFECTED, exact SHA256, engine/version, keyId and HMAC-SHA256 signature. Canonical signed message is fileUUID:sha256:byteSize:status:engineUTF8ByteLength:engine:challenge. The signing key bytes exist only at the approved scanner and in a private operator-controlled FinanceScanAuthority row. Runtime database credentials cannot read that row or invoke signing helpers. Database source/state guards independently check the signature, file binding and decision. A caller cannot supply a scan result to the public API. Unavailable/malformed/unsigned scans retain quarantine; infected files are unavailable. There is no production clean fallback.

Downloads use an authenticated proxy and verify current access before fetching bytes and again before responding. Only CLEAN files qualify; immutable hash/size/type are rechecked. Each byte-range response is at most3MiB; the browser assembles up to10MiB, checks complete SHA256 and then offers the file. Every range requires current access. No reusable download URL exists, and a revoked user cannot start another range. Headers are private/no-store, safe attachment disposition, nosniff and exact content range/hash. A response already delivered while authorized cannot be unsent.

This bounded protocol addresses the documented [Vercel payload limit](https://vercel.com/docs/functions/limitations). The provider's [private buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals) and [Storage access controls/service-key boundary](https://supabase.com/docs/guides/storage/security/access-control) support the storage boundary. Finance-page CSP permits only the exact configured finance signed-upload path; ordinary pages retain their existing connection policy.

Draft removal first commits an immutable-history tombstone, then attempts object deletion. A failed deletion remains visibly pending and is retryable without restoring download access. Posted-source removal is blocked by both checked command and raw state guard. Scanner key versions cannot be overwritten or deleted; rotation creates a new key and retires the prior one through controlled operator administration.

## Operator setup

No scanner or signing secret is configured live by this delivery. Keep FINANCE_SCANNER_URL/FINANCE_SCANNER_SECRET server-only. The endpoint must use HTTPS outside isolated loopback tests, does not redirect, accepts raw bytes with X-Content-SHA256/X-Finance-File-Id/X-Finance-Scan-Challenge and returns the signed JSON above. The bearer secret and signing key are separate. Approve the scanner/data-processing arrangement before using real evidence.

pnpm finance:scanner consumes one0600 regular JSON file under .local/finance through FINANCE_CREDENTIAL_FILE, using a controlled operator database connection. Fields: cookie, password, optional code, reason, keyId UUID, name, signingSecretHex (32–128 decoded bytes). The command freshly verifies the current Finance Owner and session under ownership/grant locks, creates an immutable verification-key version, audits only its ID/name and deletes the private credential file. It never prints credentials or the signing key. No public key-management route exists.

pnpm finance:evidence:cleanup uses the same private authentication-file discipline with cookie/password/optional code/reason and an explicit olderThanHours approved by the company. Default is a dry run, maximum ten candidates: abandoned RESERVED files on DRAFT sources and pending removal tombstones. Add --apply to perform that bounded cleanup. Current access and parent state are rechecked; posted evidence is retained. No retention period or scheduled destructive job is silently enabled. Keep posted evidence until an approved retention policy is separately implemented.
