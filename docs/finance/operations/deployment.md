1. Select the reviewed PR/head and verify its exact fresh CI result, migration source hashes and final report. Keep runtime finance disabled. Provision an isolated Supabase staging project with separate private Storage and Auth; do not borrow live finance records for test fixtures.

3. Configure server-side DATABASE_URL using the provider pooled endpoint for serverless runtime; use DIRECT_URL with the migration connection for migrations. Keep migration credentials out of browser/runtime exposure. Use AUTH_PROVIDER=supabase, APP_URL, SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY and server-only SUPABASE_SECRET_KEY; configure existing CRON_SECRET and signed scanner settings privately. Never put secrets in NEXT_PUBLIC variables or this report.
4. On the selected exact source, run `pnpm install --frozen-lockfile`, `pnpm db:generate`, then `pnpm db:migrate:deploy` using the explicitly selected staging target. The migration target guard may require its documented hosted acknowledgement. Do not bypass it or reuse local test URLs. Apply immutable migration order through84 and any later reviewed additive migration; never edit an applied file.
5. Apply/review `supabase/setup.sql` using the migration operator. Verify runtime SELECT-only financial tables, checked-function execute grants, private helper revokes, anon/authenticated denial, RLS and private bucket/scanner configuration. Setup must not widen financial access. Reverify the same checks after any provider setup changes.
6. Deploy the selected source to a protected Vercel preview with finance still disabled. Verify ordinary ERP login, assignments, attendance, HR leave approval and announcement workflows. Build alone is insufficient.
7. Only after the owner/security/policy review, use the existing fresh-auth owner setup workflow in the explicit staging environment. Intended owner is zablerkhanahmad@gmail.com; that email is not an automatic grant. Require current active Super Admin status, explicit selection and current provider MFA where required. Use protected local credential input; never paste passwords or API keys into issue/PR/report text.
8. Record approved chart, PKR reporting, fiscal calendar, bank-credit/tax/depreciation/investment/funding policies and opening cutover evidence. Import only through reviewed preview/approval with zero-clearing proof and independent GL/subledger reconciliation. Synthetic fixtures must not become company books.
9. Rehearse owner/selected/unselected/lower-role access, real file scan/upload/download, revocation, exports, source corrections, reports and scheduled draft recovery in staging. Record actual outcomes. Separately obtain the launch decision before changing the live flag/grants/imports.

## Release and stop conditions

[Final acceptance](../review/owner-review-pack.md) records the exact source and evidence, human review and remaining risks. A failing financial control, unavailable private evidence, unmatched cutover, incorrect permission, unresolved migration or unreviewed policy keeps finance disabled. Do not silently post a balancing adjustment, assume tax, delete retained history or mark a failed report final to force acceptance.

During an incident, disable finance and stop finance workers; preserve logs privately, the exact source/head, migration receipts and financial history. Revoke exposed sessions/access as appropriate through the checked owner/provider workflow. Roll back compatible application code while leaving the additive schema and retained source/GL intact. Restoring database plus object evidence requires a separately approved target/point and independently reconciled balances, rather than overwriting live books as a test. Recheck ordinary ERP and private finance boundaries before any later enablement. No billing upgrade is authorized by this runbook.
