# Tables, account security and recovery

Tables opens scoped People, Tasks, Attendance and Report status. Filters/sorting/pagination run against current role and membership. Personal saved views never grant additional access. Visible export columns are checked again server-side; exports stop at 10,000 rows and neutralize spreadsheet formulas. Inline editing uses existing versioned services. Recorded attendance opens its effective/raw/correction history; it cannot be overwritten in a table.

Task CSV import uses UTF-8, at most 2 MB/500 tasks, required title/assignee/reviewer usernames and optional description/priority/due_at. Preview reports row errors without writing tasks. A valid preview expires in 15 minutes and is private to its creator. Commit rechecks active project membership, independent review, current manager and archive state. Bulk priority/deadline changes allow at most 100 selected tasks, require a reason and reject the entire commit if any version/permission changed. A committed preview returns its receipt on replay and scrubs input payloads.

Account security is available through the sidebar footer, including HR without adding another HR menu. Supabase owns TOTP secrets, challenges and verified assurance. App responses expose a setup key/QR only for the current user's new enrollment and never record it in audits, idempotency receipts or documentation. A verified factor requires AAL2 for normal workspace access; the security screen remains accessible for verification. Only an AAL2 Super Admin can enable the optional privileged-policy setting. It is initially off; do not enroll the owner or activate it without their involvement. Losing a verified factor requires the provider's account-recovery procedure and identity verification by the owner; administrators cannot silently bypass the factor through normal app controls.

Supabase sign-in/recovery callbacks register a provider session_id linked to the ACTIVE domain person. Requests require both provider verification and the app session registration. Local sign-out removes that session; all-device sign-out removes all app registrations before requesting global provider sign-out. Role/status/reactivation clears old registrations. Thus an unexpired provider JWT cannot restore workspace access after revocation; sign in again. Provider access JWTs themselves remain valid until expiration, as explained in [Supabase sign-out documentation](https://supabase.com/docs/reference/javascript/auth-signout). Browser database/storage roles have no direct app-table/private-bucket access. Deployment of migration seventeen requires existing users to sign in again; credentials and records remain intact.

Production scripts use nonce-based script CSP, deny framing and object sources, constrain connections/forms/base URLs, and disable camera/microphone/geolocation. Styles retain unsafe-inline for existing React inline styles; this is not a claim of a nonce-only style policy. Nonces differ per request and pages render dynamically. Keyboard/browser and automated WCAG A/AA checks cover representative screens; automated checks do not replace inclusive manual acceptance.

Run `pnpm exec tsx scripts/verify-recovery.ts` with PostgreSQL client paths PG_DUMP_BIN/PG_RESTORE_BIN if not on PATH. The script permits only loopback encova_test and encova_restore, resets only the restore target, compares all public table counts/fingerprints and checks the source stayed unchanged. Stop test writers first. Private dumps/evidence live under .local/recovery and must never be committed. This is an isolated recovery drill, not proof of a hosted provider backup/PITR restore or Storage object restoration.

Run `pnpm exec tsx --conditions=react-server scripts/verify-performance.ts` only against loopback encova_test. It creates 100 new synthetic members, measures 100 domain-service requests at concurrency 10, and retires only its owned fixtures. Its timings exclude hosted HTTP/auth/network latency and do not establish a 100-concurrent-user production SLA. Broader company load/pilot acceptance requires an agreed workload and hosting plan.

The daily scheduler remains protected by CRON_SECRET. Its schedule discriminator follows [Vercel's documented cron headers](https://vercel.com/docs/schedules/cron-jobs); manual execution must not be reported as a natural invocation. Recovery and rollback must preserve immutable history and forward-compatible migrations. Never roll back the live database to remove an additive schema during an application rollback.

## Hosted-source logical recovery follow-up

`pnpm exec tsx scripts/verify-hosted-recovery.ts` requires RECOVERY_ACK=encova-hosted-to-isolated-local, the selected project's controlled RECOVERY_DATABASE_URL on the session pooler, verified CA and Storage credentials, and working PostgreSQL clients. The target is strictly loopback encova_restore; source project/username matching is checked. Export uses a read-only consistent snapshot; only the local restore schema is reset. The source public ERP schema is never written. Storage copies go to a newly created private bucket with an owned encova-restore prefix, then are checksum-verified, checked for anonymous denial and removed. The original bucket and objects are never overwritten/deleted. Private dumps/manifests/object bytes remain under .local/recovery with restricted permissions.

This validates actual hosted ERP records and object bytes through a logical restore. Auth schema/identities, managed provider PITR/regional failure, automated off-site backup scheduling and owner retention decisions are separate. Do not replace those claims with the existence of a local dump or bucket copy. A new hosted recovery project or paid backup feature is not purchased automatically.
